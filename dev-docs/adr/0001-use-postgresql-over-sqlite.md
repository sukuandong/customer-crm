## 背景

项目初始化版本（`fddc372`）使用 SQLite 文件数据库，数据落在 `backend/data/crm.db`。
2026-11-21 的提交 `aab4a6b` 将数据层整体迁移到 PostgreSQL 18，后端路由同步改为全 `async`。

> 说明：原提交信息只记录了"做了什么"，没有记录"为什么"。以下理由是根据改动内容补录的推断，
> 请当事人在 review 时确认或修正——这正是 ADR 要解决的问题。

## 备选方案

1. **保留 SQLite**：零外部依赖、启动最简单，但并发写入能力弱，与 async 驱动生态配合有限。
2. **PostgreSQL 18 + SQLAlchemy 2.0 async + asyncpg**（选用）：需要外部数据库服务，但连接池、并发与异步支持完整。
3. **其他托管数据库**：未在当前改动中出现，无记录。

## 决策

数据层采用 PostgreSQL 18，通过 SQLAlchemy 2.0 async + asyncpg 连接池访问；所有路由改为 `async`；连接串由环境变量 `DATABASE_URL` 提供。

## 理由（补录推断）

- asyncpg 是异步驱动，与 FastAPI 全异步路由匹配，避免同步数据库调用阻塞事件循环
- 连接池（`pool_size=5`、`max_overflow=10`、`pool_pre_ping`、`pool_recycle=1800`）适合多请求并发场景
- 与团队后续可能使用 GCP 托管数据库的路线一致（需确认）

## 后果

**正面**
- 全链路异步，数据库访问不再阻塞事件循环
- 数据结构与管理能力比本地文件库更完整

**负面 / 代价**
- 本地启动多一个前置条件：必须先有 PostgreSQL（README 提供 Docker 命令）
- 连接串需要环境变量；密码中的 `@` 必须 URL 编码为 `%40`，配置容易出错
- `init_db()` 只建表不迁移，后续字段变更需另找方案

**需要后续跟进的事**
- 确认补录的理由是否准确
- 如数据模型要持续演进，另写 ADR 选择迁移工具（如 Alembic）
